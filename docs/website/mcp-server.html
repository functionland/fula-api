Fula MCP Server

Let AI assistants store and read files in your own encrypted Fula workspace

🤖 Works with Claude, ChatGPT, Gemini, Codex 🔐 End-to-End Encrypted 🔑 Never Sees Your Master Key 🧩 Model Context Protocol

What It Is

The Fula MCP server lets AI assistants — like Claude, ChatGPT, Gemini, or Codex — store and read files in your Fula AI workspace. Files the AI writes are encrypted in exactly the same end-to-end-encrypted format the FxFiles app uses, so they appear right alongside your own files in FxFiles.

The important part: the AI does this without ever getting the key that decrypts your other files. It is handed a dedicated workspace key that unlocks only its own AI workspace — nothing else. Your master encryption key never leaves your device and is never given to the AI or to any server.

MCP (Model Context Protocol) is the open standard AI assistants use to connect to external tools. The Fula MCP server is one such tool: it exposes a small set of "store / read / list / search / tag" file operations that the AI can call.

🤖 For your AI assistant

Give an AI a place to keep notes, documents, and results that persist across chats — encrypted, decentralized, and owned by you.

🔐 Same encryption as FxFiles

Every file the AI stores is individually encrypted in the FxFiles format. Open FxFiles and the AI's files are simply there, decryptable by you.

🔑 Your other files stay private

The AI receives a workspace-only key derived one-way from your master key. It cannot reverse it, and it cannot reach your real files.

🧩 Built on an open standard

Works with any MCP-capable assistant. No proprietary plugin — just the standard Model Context Protocol.

Two Ways to Use It

There are two ways to connect an AI to your Fula workspace. Pick the one that matches your AI assistant:

💻 Local binary

For desktop / terminal AI tools that run on your own computer — Claude Desktop, Claude Code, Codex CLI, Gemini CLI. The MCP server runs locally on your machine. No build step: it starts with a single npx command. This is the path that is available today.

🌐 Hosted server

For web AI assistants that can only reach a URL — Claude.ai, ChatGPT (web). You add a hosted server URL as a custom connector and sign in. This path requires a hosted server to be deployed first (see below).

Not sure which? If your AI runs as an app or in a terminal on your computer, use the local binary. If you use the AI through a website, you need the hosted server.

Local Binary Setup

The local server is published as an npm package, @functionland/fula-mcp. You never build anything — npx downloads a verified, prebuilt binary for your platform the first time it runs and caches it. Your AI client launches it automatically.

npx @functionland/fula-mcp

In every example below you paste a connection bundle into the FULA_MCP_CAPABILITY environment variable. You get that bundle from the FxFiles app (see How to Connect). It contains your scoped, workspace-only access — not your master key.

Tip: Run npx -y @functionland/fula-mcp once in a terminal first. This warms the binary cache so your AI client does not time out waiting for the first download.

Claude Desktop

Edit claude_desktop_config.json (on Windows: %APPDATA%\Claude\claude_desktop_config.json; on macOS: ~/Library/Application Support/Claude/claude_desktop_config.json) and add a fula entry under mcpServers, then fully quit and reopen Claude Desktop:

{
  "mcpServers": {
    "fula": {
      "command": "npx",
      "args": ["-y", "@functionland/fula-mcp"],
      "env": {
        "FULA_MCP_CAPABILITY": "<paste your connection bundle from FxFiles>"
      }
    }
  }
}

Claude Code

Claude Code stores MCP servers in the same mcpServers shape (in .mcp.json). The simplest way to add one with an environment variable is the add-json command:

claude mcp add-json fula '{
  "type": "stdio",
  "command": "npx",
  "args": ["-y", "@functionland/fula-mcp"],
  "env": { "FULA_MCP_CAPABILITY": "<paste your connection bundle from FxFiles>" }
}'

Use --scope user to make the server available across all your projects, or --scope project to share it with a repo via a checked-in .mcp.json.

Codex CLI

Codex reads MCP servers from ~/.codex/config.toml. Add a server section — note the table name is mcp_servers (with an underscore), and the environment variables go in a nested .env table:

[mcp_servers.fula]
command = "npx"
args = ["-y", "@functionland/fula-mcp"]

[mcp_servers.fula.env]
FULA_MCP_CAPABILITY = "<paste your connection bundle from FxFiles>"

Or add it from the command line:

codex mcp add fula --env FULA_MCP_CAPABILITY="<bundle>" -- npx -y @functionland/fula-mcp

Gemini CLI

Gemini CLI uses the same mcpServers object in its settings.json:

{
  "mcpServers": {
    "fula": {
      "command": "npx",
      "args": ["-y", "@functionland/fula-mcp"],
      "env": { "FULA_MCP_CAPABILITY": "<paste your connection bundle from FxFiles>" }
    }
  }
}

Note: The @functionland/fula-mcp package and its config shape match the package's own README. MCP client configuration formats do change between releases — if an example does not match your installed version, check that client's current MCP documentation and use its mcpServers / mcp_servers equivalent with the same command, args, and FULA_MCP_CAPABILITY environment variable.

Hosted Server Setup

Web-based AI assistants (Claude.ai, ChatGPT on the web) cannot launch a local program — they can only reach a server over the internet. For those, you connect to a hosted Fula MCP server:

  • In the AI assistant's settings, add a custom connector and paste the hosted server's URL.
  • Sign in (OAuth) when prompted, to link the connector to your Fula account.
  • The AI can then store and read files in your AI workspace, the same way the local binary does.

Availability: The hosted server is not a public service yet. It is designed to be self-hosted so you stay in control of your own trust domain. Until you (or your organization) deploy one, only the local binary path is available. The hosted server lives in the Fula API repository; follow the repository's setup notes to deploy your own.

How to Connect

You grant an AI access from inside the FxFiles app, under AI Connections. You stay in control: you create the connection, and you can disconnect it at any time.

Connect an AI (local)

Choose "Connect an AI". FxFiles creates a one-time connection bundle for you to paste into your AI client's config (the FULA_MCP_CAPABILITY value above).

Connect a hosted AI

Choose "Connect a hosted AI" to pair a web assistant with your hosted server by URL (the OAuth flow above).

Disconnect anytime

Each connection is listed in FxFiles. Disconnect to cut off future access — see exactly how that takes effect in the security section.

The bundle is sensitive. The connection bundle carries your workspace access. Treat it like a password: do not share it or commit it to a public repository. (It still cannot reach your non-workspace files — but anyone holding it can use your AI workspace until you disconnect.)

What the AI Can Do

The MCP server exposes a small, fixed set of file operations. The AI can only call these, and only within its own workspace (plus any specific file you explicitly share with it):

STORE store a file

Save a file into the AI's encrypted workspace. The file is individually encrypted and shows up in your FxFiles library.

READ read a file

Read back a file from the workspace (or a specific file you granted the AI access to). Anything outside that scope is refused before any network request is made.

LIST list files

Enumerate the files in the AI's workspace, optionally narrowed by category or sub-folder.

SEARCH search files

Find workspace files by filename (case-insensitive substring match).

TAG tag a file / list tags

Apply tags to a stored file, and list the tags in the workspace — written in the same tag format FxFiles uses, so your app can adopt them.

Scope is enforced, not advisory. Every operation is checked against the workspace scope before any work happens. A request for a key outside the AI workspace is denied outright.

Security, Privacy & Data Protection

This section states what is guaranteed and what the honest limits are. We do not claim more than the design delivers.

Guaranteed: the AI can never reach your other files on its own

This is the one absolute guarantee, and it holds for both the local binary and the hosted server: the AI can never reach your other files on its own — without an explicit action by you (the single, owner-initiated exception is described just below). It rests on two independent mechanisms — either one alone would block access to your other files; both must be defeated for any leak, and the second does not depend on the cryptography of the first:

  • 1. The master key is never shared. The AI never receives the master key that decrypts your real files. It receives only a dedicated AI-workspace key, computed as a one-way derivation of your master key (a BLAKE3 key-derivation under a fixed, workspace-specific label). One-way means the AI cannot work backwards from the workspace key to your master key, and the workspace key unlocks only the AI workspace — not your real files, not anything else.
  • 2. The storage gateway independently enforces scope. The AI's access token is restricted by the storage gateway itself to the AI-workspace bucket and operations. Even if the encryption were somehow bypassed, the gateway still refuses any request outside that scope. Crucially, isolation between different users comes from the gateway opening storage per account (keyed to your hashed user id and the token's subject) — not merely from a path prefix.

What "your other files" means: your real FxFiles library, encrypted under your master key, is never reachable by the AI on its own. The one exception is intentional and owner-initiated: if you explicitly share a specific file with the AI, it can read that file — and nothing else. The AI can never reach your files unilaterally.

Your AI workspace — local binary

With the local binary, the connection bundle lives in your AI client's configuration file on your own computer. The server is stateless: it loads the bundle into memory at startup, never writes secrets to disk, and never logs them.

Your responsibility: because the bundle sits in a config file on your machine, keep that file secure (do not paste it into shared chats or public repos). Anyone who obtains the bundle can use your AI workspace until you disconnect — after which their current session still runs until its short-lived token expires (about an hour by default, up to 24). They still cannot reach your other files or your master key.

Your AI workspace — hosted server

Status — read first: the hosted server is not deployed as a public service. Everything in this subsection describes the intended design of the self-hosted server, not a running system you can rely on today. Deploy your own (see Hosted Server Setup) to obtain these protections.

By design, the hosted server is built so that a stolen database or disk reveals nothing useful: it stores your workspace key encrypted, with the encryption key held in your own self-hosted OpenBao (a separate secrets vault — a distinct trust domain). The server must call OpenBao to decrypt a workspace key in order to serve a request. (This holds as long as your OpenBao unseal/root keys are not kept on the same machine as the database.)

Honest limit of any hosted server: a stolen database or disk alone reveals nothing (the keys are encrypted, and the vault key is elsewhere). But a live, fully-compromised server — one an attacker actively controls while it is decrypting to serve requests — could read the workspaces of currently-active sessions. This is unavoidable for any server that decrypts data to hand it to an AI. Even then, it can never reach your master key, and never your other (non-workspace) files. Running the server yourself keeps that risk inside your own trust domain.

Connection model & revoking access

You connect once, and it keeps working until you disconnect. The AI carries a short-lived session token (about an hour by default, and at most 24 hours if a server is configured for a longer lifetime) and cannot renew it on its own.

When you Disconnect a connection in FxFiles, the pairing is removed immediately, so the AI gets no new access from that moment. Its current session keeps working only until the short-lived token expires — about an hour by default, and up to 24 hours at most — and then it is permanently locked out.

Honest limit: "Disconnect" is not an instant kill switch for a session already in progress; it stops renewal and lets the short-lived token run out (default ~1 hour). A near-instant (~30 second) server-side token-revocation deny-list exists in the gateway but is off by default, and wiring "Disconnect" to trigger it is a planned follow-up — so today, disconnect is expiry-bound. Files the AI already stored remain in your library.

Encryption

  • Every file is individually encrypted with its own random per-file key (a fresh data-encryption key per file), using authenticated encryption (AES-256-GCM by default; ChaCha20-Poly1305 is also supported).
  • Per-file keys are wrapped to recipients, so a file the AI writes can be unwrapped by you (its owner) without exposing any other file's key.
  • Metadata privacy. Filenames and paths are not stored in the clear: storage keys are obfuscated (hashed), and the index that maps your logical paths to stored objects is itself encrypted. An observer of raw storage does not learn your filenames or folder structure.

In short: the guarantee that the AI cannot reach your other files on its own is absolute (two independent mechanisms, local and hosted alike); the only way it reads a real file is if you explicitly share that one file. Workspace privacy is strong but has the honest limits stated above — a stolen local bundle, or a live-compromised hosted server, can expose the AI workspace (never your master key, never your other files). We deliberately do not claim "100% everything."
